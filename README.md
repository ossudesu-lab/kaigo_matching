# kaigo_matching — 短期入所 空床マッチング支援アプリ

**アプリ: https://kaigomatching.vercel.app**

短期入所（ショートステイ）施設向けに、空床が出たときに「どこの誰に声をかけるか」を助けるアプリ。

利用記録（誰をどの居宅介護支援事業所から受け入れて、事前情報とのズレやトラブルがあったか）を貯めておくと、
居宅介護支援事業所（ケアマネ）ごとの傾向が自動集計され、優先順位付けと連絡文の下書きが得られる。

## できること

- 利用記録の入力（フォーム、または記録文からのAI抽出）
- 居宅・担当者別の集計（信用スコア＝事前情報とのズレの少なさ／トラブル率）
- 空き枠に対して、誰に声をかけるべきかの優先順位表示
- 連絡文（下書き）のAI生成

送信機能はデモで、実際にはメール等を送信しない。

## 技術構成

フロント（Vite + React）と、Anthropic API キーを扱うサーバー関数（`/api`）の2層構成。
APIキーはサーバー側の環境変数にのみ置き、ブラウザには一切出さない。

```
index.html               エントリHTML
vite.config.js           ビルド設定
src/
  main.jsx                起動（storage シムを先に読む）
  storage.js               window.storage 互換シム（無ければ localStorage を裏に置く）
  App.jsx                  本体アプリ（単一ファイルのReactコンポーネント。AI呼び出しは /api を叩くだけ）
api/
  extract.js               記録の抽出（HTTP層のみ。プロンプトは _lib に置く）
  draft.js                 連絡文の生成（デフォルト Sonnet）
  _lib/
    extract-prompt.js       抽出プロンプトとモデルの定義（本番とevalが共有する唯一の正）
    anthropic.js            Anthropic 呼び出し共通（APIキー・max_tokens を固定）
    ratelimit.js             簡易レート制限（インメモリのベストエフォート）
scripts/
  eval-extract.js          抽出evalの実走（CLI/CI用）
  eval-scoring.js          採点ロジック
  smoke-test.js            デプロイ経路の疎通確認
  prompt-variants/         比較用に保存した過去のプロンプト
eval-cases.json           evalの正解データ（開発用19件 + 未知16件）
eval-app.jsx              抽出evalの表示用デモ（Claude.ai アーティファクト版。正は scripts/）
draft-eval.jsx            連絡文eval（LLM-as-judge）
```

プロンプトの定義を `_lib/extract-prompt.js` の1箇所に置き、本番APIとevalの両方がそこを
import している。以前は本番とevalが別々のプロンプトを持っており、evalで検証した改善が
本番に反映されていない状態が発生した（詳細は下記「わかったこと」）。

## 精度の測り方（eval）

このアプリの中核は「介護記録の文章から8項目を構造化して取り出す」ことなので、
**その精度をどう測っているか**を公開しておく。

### 採点の考え方

35ケースの正解データ（`eval-cases.json`）に対し、フィールドごとに重み付けで採点する。

- **見逃し(FN)は過剰(FP)より重く減点する。** 現場で本当に困るのは「拾えなかった」ケースのため
- **要介護度は1段階違いに部分点0.5。** 完全な外れと区別する
- **weight と critical は別の軸。** weight は減点の重さ、critical は「黙って間違えられては困るか」。
  利用日は weight 1 だが critical（集計の軸なので、黙って壊れると集計結果そのものが狂う）

### 開発用と「未知ケース」を分けている

プロンプトのチューニングに使ったケースだけで測ると、点数は「作り込んだケースで正解できる」
ことしか示さない。そこでプロンプトを作った**あと**に追加したケースを `heldOut` として分け、
別々に集計している。

```
総合スコア（全35件）
 ├ 開発用（19件・プロンプト作成に使用）
 └ 未知（16件・作成後に追加）← 汎化性能
```

未知ケースを見てプロンプトを直した場合、そのケースは開発用に格下げする。
使ったケースを未知のまま数えると、避けたはずの過学習を自分で再生産することになるため。

**実際に5件を格下げしている**（v5・v10・w6・w8・w11）。いずれも不合格を見てプロンプトを
直したケースで、格下げの理由は `eval-cases.json` の `intent` に1件ずつ書いてある。

### 現在のスコア（Claude Haiku 4.5）

| | スコア |
|---|---|
| 開発用 19件 | 100 |
| 未知 16件 | 99 |

### モデル選定の根拠

抽出は Haiku を使っている。「構造化タスクだから Haiku で十分だろう」という仮定ではなく、
同じevalを両モデルで回して決めた。

| | Haiku 4.5 | Sonnet 5 |
|---|---|---|
| 総合スコア | 100（100–100） | 100（99–100） |
| 全10回満点のケース | 14/14 | 11/14 |
| 応答時間（中央） | 1.45秒 | 3.54秒 |
| 1,000件あたりのコスト | $1.74 | $6.53 |

精度は同等で、約2.4倍速く、約3.7倍安い。

（コストはこの測定時点のもの。その後プロンプトに判断基準を書き足したため入力トークンが増え、
Haiku は現在 **$2.34/1,000件**。下の表の数字がこちら）

（この比較は未知ケースを追加する前、開発用14ケースで実施したもの。両モデルとも100点に
張り付いており、**このevalはモデルの能力差を測れる状態にない**。差が出たのは満点回数と
速度・コストだけで、「Haikuの方が賢い」とは言えない）

### ローカルLLMとの比較（35ケース × 3回）

記録は要配慮個人情報を含むため、外部APIに出せない事業所がある。
ローカル実行（Ollama）で代替できるかを実測した。`--model=ollama:qwen2.5:7b` で切り替わる。

| | Haiku 4.5 | qwen2.5:7b<br>本番プロンプト | qwen2.5:7b<br>ローカル調整版 |
|---|---|---|---|
| 総合スコア | 100 | 94（93–95） | 96（95–96） |
| 　├ 開発用 19件 | 100 | 94 | 94 |
| 　└ 未知 16件 | 99 | 94 | 98 |
| 重大な見逃し | 0.0 件/回 | 11.7 件/回 | 9.0 件/回 |
| 応答時間（中央） | 1.62秒 | 42.87秒 | 41.68秒 |
| 1,000件あたりのコスト | $2.34 | $0 | $0 |

**結論：代替にはならない。** 総合96点は一見高いが、**重大な見逃しが9件/回**ある。
重み付き採点では軽い項目が落ちても総合点が動かないため、総合点だけを見ると実力を見誤る。

プロンプトを7B級向けに調整（1,269→830トークン、条件の入れ子と否定文を削減）すると
94→96に上がったので、**素の比較だけで「ローカルは使えない」と結論づけるのは早い**。
ただし調整しても差は埋まらなかった。

調整で分かったこと:

- **v7（認定申請中は要介護度を空に）76→94** — これは指示の書き方の問題だった
- **v4（例示にない看護処置＝経管栄養）82→88** — 「これは例です。挙げていない処置も含めてください」と
  明示しても安定しない。ただし3回では判断できない（後述の30回ルール）ので、**直ったとは言えない**
- **未知98 > 開発用94 と逆転した** — 短くしたぶん trouble と discrepancy の排他ルールが緩み、
  本番プロンプトが時間をかけて詰めた部分が落ちている（t4=74・s6=84・t2=84）

外部に出せない事業所向けの逃げ道としては成立するが、既定にはしない。

### わかったこと・やらなかったこと

わかったこと:

- **evalが満点でも、本番が壊れていることがある。** 本番APIとevalが別々のプロンプトを
  持っていた時期があり、利用日が全ケースで取れていなかった。にもかかわらず総合点は91点、
  重大な見逃しは0件で、**フィールド別スコアを開くまで気づけなかった**。
  重み付き採点は、軽い項目が全滅しても総合点がほとんど動かない
- **10回の実行では、ケース別の安定性は判断できない。** 同じプロンプトのまま
  「10/10回満点 → 7/10回満点」と振れる。30回まわして初めて約50%失敗が実態だと分かった。
  10回の振れを改善・劣化と読み違えると、存在しない問題を追いかけることになる
- **検査は、見ている範囲の外を測れない。** PIIマスキングの漏れ率が0%と出ていたが、
  検査が `staff` / `kyotaku` しか見ておらず、「当施設の看護師・鈴木」は伏せられていなかった。
  **「0%」を見たら、まず測定対象の範囲を疑う**

やらなかったこと（理由つき）:

- **v6（担当ケアマネの交代）の修正** — 約50%失敗するが、あえて直していない。
  直すとこのケースも開発用に格下げになり、未知ケースが減るため。
  プロンプトを触ったときの劣化検知に使う。`eval-cases.json` に実測値つきで記録している
- **連絡文eval（`draft-eval.jsx`）のCLI移行・CI化** — 抽出evalのみ移行済み。
  連絡文側は LLM-as-judge を使うため、**審判そのものの検証が別途必要**で、
  そこを済ませないままCIに載せても「審判が見つけられていないだけ」を通してしまう。
  このアプリのAI機能のうち、**連絡文生成には自動evalが無い**状態
- **実際の記録での検証** — 35ケースはすべて自作。実記録は要配慮個人情報のため使えない。
  現場14年の経験から書いているが、**1人が正解を決めている**という限界は残る

### CI（GitHub Actions）

`api/_lib/extract-prompt.js` / `eval-cases.json` / `scripts/**` を触るPRで自動実行し、
結果をPRにコメントする（`.github/workflows/eval.yml`）。

**落とすのは完走率90%未満のときだけで、スコアでは落とさない。** スコアで落とすと、
基準に届かせるために未知ケースを削るなどの誘因が生まれるため。
実際にクレジットが尽きて1/3回しか完走できなかったとき、この条件が結果の採用を止めた。

### 回し方

```console
node --env-file=.env scripts/eval-extract.js --runs=10
node --env-file=.env scripts/eval-extract.js --cases=v6 --runs=30   # 特定ケースの安定性
node --env-file=.env scripts/eval-extract.js --model=claude-sonnet-5
node scripts/smoke-test.js --url=https://kaigomatching.vercel.app   # デプロイ経路の疎通確認
```

完走率が90%を下回ると終了コード1を返す（欠けたデータの平均は実力ではないため）。

運用ルールの詳細は [CLAUDE.md](CLAUDE.md) の「eval の運用ルール」を参照。

### 経緯

このevalを作る過程と、そこで踏んだ落とし穴は Zenn に3本にまとめた。
いずれも「作り方」ではなく「測定そのものを疑った」記録。

1. [プロンプト改善を「1回の満点」で判断してはいけない ─ 10回回して分かったこと](https://zenn.dev/ossudesu/articles/zenn-eval-article)
   evalを自作し、1回の満点が運だったと分かるまで
2. [evalは満点だった。本番は利用日を1件も取れていなかった](https://zenn.dev/ossudesu/articles/zenn-eval-heldout-article)
   その満点が本番を測っていなかった話と、未知ケース（heldOut）での測り直し
3. [マスキングの漏れは0%だった。検査が見ていない名前があった](https://zenn.dev/ossudesu/articles/zenn-pii-masking-article)
   PIIマスキングの漏れ率0%が、検査の対象範囲が狭かっただけだった話と、
   外に出せない場合のローカルLLMとの比較

## セキュリティ上の注意（やったこと・やらなかったこと）

個人ポートフォリオのデモとして公開する前提での対策。詳細は [DEPLOY.md](DEPLOY.md) を参照。

やったこと:

- APIキーをサーバー側に隠す（ブラウザに渡さない）
- 出力トークン上限（`max_tokens=1024`）をサーバーで固定、クライアントから指定不可に
- 入力サイズの上限をサーバーで検証（記録文は4000文字まで）
- レート制限（IPごと20回/10分、全体200回/10分。インメモリ・ベストエフォート）
- Anthropicのクレジット残高を少額に固定、自動リロードは無効
- `.gitignore` に `.env` があることを確認してから公開

やらなかったこと（理由つき）:

- レート制限の共有ストア化（Redis等） — 残高上限が最後の壁になるため、個人デモの規模では割に合わないと判断
- 認証 — デモとして誰でも触れる状態にしている
- WAFやbot対策の導入
- 本番相当の監視・アラート

制限を知らずに素通りしたのか、知ったうえで選ばなかったのかを外から区別できるように、ここに明記している。

### PIIマスキング（氏名を外部APIに渡さない）

介護記録には利用者名・担当ケアマネ名・自施設職員名が生で入る。
`MASK_PII=1` で、送信前に仮ID（`[人物1]` `[事業所1]`）へ置き換え、返ってきた結果を戻す。
守る境界は「**第三者である Anthropic に氏名を渡さない**」ところ。

抽出して返す必要がある `staff` / `kyotaku` は復元し、利用者名・自施設職員名は復元しない。
置き換えても文の構造は残るので、「当施設の看護師・[人物1]」のような文脈から
「これは紹介元の担当ではない」という判断はモデル側でそのままできる。

実測（35ケース）:

| | 辞書あり | 辞書なし（＝初めての相手） |
|---|---|---|
| 伏せ漏れ | 0/35 | 0/35 |
| 復元一致 | 35/35 | 34/35 |

抽出精度は **マスクあり99 / なし100**（Haiku・3回実行）。落ちたのは v6 だけ。

```bash
node scripts/pii-leak-check.js     # 漏れ率の測定（API課金なし）
```

**これで十分ではない、という前提も書いておく。** 氏名を伏せても要介護度・医療処置・
夜間の様子といった**要配慮個人情報は本文に残る**。施設と時期が分かれば個人が特定されうる。
これは「送る情報を減らす」措置であって、「個人情報を送っていない」と言い切れるものではない。
外に一切出せない場合の答えは上のローカルLLM側。

作る過程で踏んだ穴:

- **モデルが角括弧を外して返す。** `[事業所1]` ではなく `事業所1` と書いてくるため、
  角括弧を必須にしていた復元が全滅し、`staff` と `kyotaku` が**0点**になった
- **敬称のない名前が素通りしていた。** 「当施設の看護師・鈴木」は伏せられていなかったのに、
  漏れ率は0%と出ていた。**漏れの検査が `staff` / `kyotaku` しか見ていなかった**ため。
  抽出対象でない氏名を `piiNames` として正解データに足して塞いだ
- **「ケアマネさん」の「ケアマネ」を人名と誤検出していた**

残る限界は **`staff` の姓の正規化**。「鈴木花子」を伏せると、姓だけ取る判断をモデルに渡せず
「鈴木花子」のまま戻る（正解は「鈴木」）。過去の記録から作った辞書があれば正規形で戻せるが、
このAPIはステートレスで辞書を持てず、クライアントから辞書を送れば結局氏名を送ることになる。
姓をヒューリスティックで推測する案は、誤ると別人の実績に記録が積まれるため採らなかった。

このセキュリティ対策の詳しい経緯は Zenn 記事にまとめた: [LLM APIの個人デモを公開するとき、キーを隠すだけでは足りなかった](https://zenn.dev/ossudesu/articles/article-draft)

## セットアップ

```console
npm i
```

`.env.example` を `.env` にコピーし、`ANTHROPIC_API_KEY` を設定する（`.env` は gitignore 済み）。

## ローカル起動

`npm run dev`（Vite単体）は `/api` を動かせない。フロントとAPIを一緒に動かすには Vercel CLI を使う。

```console
npm install -g vercel
vercel login
vercel dev
```

`http://localhost:3000` でフロント＋APIが動く。

## デプロイ

Vercel を利用（フロント: Vite ビルド → `dist`、`/api` はサーバー関数として自動デプロイ）。
手順・環境変数・モデル切替・セキュリティ上の注意は [DEPLOY.md](DEPLOY.md) を参照。

## データの保存先

利用記録は `window.storage` の `usage-records-v1` に、差出人設定は `sender-settings-v1` に保存される
（ブラウザの localStorage/sessionStorage は直接使わない設計）。
